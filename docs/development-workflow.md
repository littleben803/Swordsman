# 开发工作流

- 更新日期：2026-10-26
- 目标：让不同 AI 环境和维护者以相同边界、小步交付项目修改

## 任务开始

先进行只读检查，不立即修改：

```bash
git status --short --branch
git diff --stat
```

工作区已有变化时，假定它们属于用户；不回退、不覆盖、不批量格式化。若与当前任务重叠且无法安全绕开，应暂停并让用户决定。

随后向用户明确产品目标、技术方案、任务边界、允许修改的文件、不允许修改的文件和验收标准。

## 阶段拆分

1. **分析**：读取代码、场景、配置和日志，形成证据化结论。
2. **方案**：给出最小修改路径、风险和回滚方案。
3. **实现**：只修改已批准文件。
4. **验证**：执行与风险匹配的检查。
5. **交付**：汇报 diff、验证、遗留问题和 Git 状态。

每阶段结束后等待用户确认。探索性实验不得直接进入正式运行路径。

## 修改策略

### C# 代码

- 保持现有风格，不做无关格式化。
- 优先局部修复，不为“现代化”引入新抽象。
- 修改 `MonoBehaviour`、`ScriptableObject` 或序列化类时，检查字段是否由 Unity 序列化。
- 不随意重命名类、文件、序列化字段或枚举值。
- 新增条件编译必须说明目标平台和未覆盖平台。
- 日志不得包含存档内容、用户标识、服务参数或敏感信息。

### 场景、Prefab 和资产

- 使用匹配版本的 Unity Editor 修改。
- 修改前记录精确目标，保存后检查 `.unity`、`.prefab`、`.asset` 和 `.meta` diff。
- 出现大量无关重序列化时停止，不自行清理或接受。
- 不批量运行资源迁移或 importer 更新工具。

### 本地大资源

`Assets/Resources/`、`Assets/Sprite/`、`Assets/Texture2D/` 不由 Git 管理。可以正常读取，但不得改变版本控制策略或批量复制、压缩、转码、上传。

若任务必须修改其中内容，先列出精确文件、备份方式、输出规格和本地交付方式。汇报时明确这些变化不会出现在普通 Git diff 中。

### 工程和依赖

修改 `ProjectSettings/`、`Packages/`、Unity 版本、插件 DLL、EasyTouch、原生插件、Bundle Identifier、版本、签名、公证或商店配置，必须单独获得许可。不能因为 Unity 提示升级或重导入就自动接受全项目变化。

## 高风险专项

### 存档

修改前必须准备当前文件名、路径、槽位和格式说明；至少一个有效旧档；兼容/迁移策略；损坏与部分写入处理；修改前后读写测试。未经确认，不改变 `PlayerPrefs` key、固定数据尺寸、字段顺序或默认覆盖行为。

### 网络和云能力

修改 `GamePHP`、云存档、激活、日志上传或支付前，必须确认功能范围、服务所有权、传输数据、用户标识、超时/重试、隐私政策和平台差异。禁止直接连接真实服务试探。

### 战斗和数值

一次只聚焦寻路、回合、AI、攻击结果或 UI 等一个职责。最低验收覆盖进入战斗、完成相关操作、状态推进、相关存取档和正常离开战斗。

## 文档维护

- 架构变化：更新 `architecture.md`。
- 当前状态或技术债：更新 `current-status.md`。
- 工作方式：更新本文件或 `AGENTS.md`。
- 验证命令：更新 `verification.md`。
- 网络、隐私、授权：更新 `security-privacy-and-licensing.md`。

新增专项文档使用小写英文和连字符，如 `save-format.md`、`battle-turn-debugging.md`、`macos-release-checklist.md`。会影响后续开发的聊天决定必须在同一阶段写回文档。

## 阶段交付

交付前执行：

```bash
git diff --check
git diff --stat
git status --short --branch
```

再按 `verification.md` 执行相应验证。汇报必须包含完成情况、新增和修改文件、未修改区域、验证命令、Debug 构建结果、遗留问题、Git 状态和下一阶段建议。

未经明确要求，不提交、不推送、不创建分支、不打标签、不发布构建。
